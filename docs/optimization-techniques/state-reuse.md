# 状态与转移复用

## 方法：区分状态等价、转移可复用和数据复制

三者省掉的工作不同，不能用一个“缓存”概念混在一起：

- 状态等价：两个状态未来的求解行为相同，可以共享价值或区间节点。
- 转移可复用：当前一步执行相同的规则分支，但后继状态依然不同；只复用这一回合的转移模板。
- 复制减负：不减少逻辑状态，只减少为隔离输入、生成键付出的开销。

最重要的区别是：不同 PP 的状态不能直接共享已求解价值。剩余资源会影响未来博弈；当前方法共享的是带约束的一步转移，而不是把满 PP 截断成较小输入。

## 例子一：相对顺序等价，不是删除顺序

构造两个除 effectOrder 外完全相同的受审计快照：

| 字段 | 快照 A | 快照 B | 私有键中的表示 |
| --- | --- | --- | --- |
| 活跃效果 X 的顺序 | 10 | 40 | 1 |
| 活跃效果 Y 的顺序 | 30 | 90 | 2 |
| 根的下一次分配计数器 | 31 | 91 | 3 |

在已审计的原生规则只需要这些计数器的相对先后关系时，两者都表示 X 先于 Y，新效果晚于两者。私有 memo 键将活跃正计数器压为排序名次，根计数器改为下一名，因此可以复用状态结果。

如果把 B 中 X、Y 的顺序反过来，归一化后两个字段分别是 2、1，仍然是不同状态。零值也保留为零。根计数器不大于活跃最大值、计数器不在限定整数范围或规则审计失败时，都不能使用这一相对表示。

这是保留行为相关信息的归一化，不是凭经验删字段。HP、PP、状态异常等仍保留；公开排序 `stateKey` 的合同也未改变。私有键使用原生 JSON 属性顺序，不同插入顺序可能导致保守的缓存未命中，不能因此错误合并。

## 例子二：从 PP=5 的一步模板安全复用到 PP=3

设其他状态与行动命令完全一致，一次原生转移对某招式的全部 PP 观察只有：执行前检查正 PP、原生扣除 1 且返回实际扣除量 1、执行后检查仍有正 PP。其余槽位也通过同样的独立审计。

1. 在初始 PP=5 的执行中，第一次检查得到约束 `初始 PP ≥ 1`。
2. 扣除 1 且返回 1 说明资源足够，累计消耗为 1。
3. 扣除后还要为正，因此约束加强为 `初始 PP ≥ 2`。该路径模板存储适用区间 `[2, ∞)` 和消耗量 1。
4. 对仅 PP 改为 3 的输入，先检查非 PP 状态与行动相同、槽位结构匹配，再检查 3 落在区间内。命中时克隆后继模板，把相应输出 PP 算成 `3 - 1 = 2`，其余状态及概率沿用已证明的转移。
5. PP=1 虽然也是正数，却不满足区间；它扣除后变为零，可能改变合法行动，必须重新模拟。PP=0 在查找键中也与正 PP 分桶隔离。

真实一回合有多个随机分支时，最终适用区间取所有分支约束的交集；同一合并后继的各分支还必须具有相同消耗向量。不能只检查最先走到的一条路径。

PP 读写如果来自未审计途径，或者 Transform 替换了招式槽位、队伍位置身份改变，就拒绝模板。Leppa 恢复、Spite、Grudge 等机制不能因为招式列表表面相同就复用。模板命中只省下一步模拟；PP=3 与 PP=5 的后继仍按真实剩余 PP 分别求解。

## 例子三：键只需要读数据，不需要复制整场战斗

PP 查找键要把正 PP 改成统一标记 1。如果一个快照同时含天气状态和 Pokémon 招式槽位，生成键时只复制“根 → sides → Pokémon → moveSlots/baseMoveSlots”的路径，并在新槽位中替换 PP；天气子树不改动，可直接读取后序列化。原快照仍保持原生 PP。

相对 effectOrder 键也只复制发生归一化的路径，再交给原生 `JSON.stringify`，避免为每个属性调用 JavaScript replacer。同一枚举分支的 outcome key 只计算一次，供后继聚合与 PP 模板构建共同使用。

但这个“只读共享”不能直接搬到战斗恢复上：恢复后的 Battle 会变异。当前快照生成保留 JSON 规范化和隔离语义；恢复时只提前复制固定版本反序列化会保留引用的 log 与 Pokémon.set，其余由原生反序列化重建。自定义 serializer 会回退完整 JSON 路径。

## 正确性边界与推广

memo、PP 模板和键的对象缓存按次 solve 重建，不跨规则变更借用旧答案。键缓存以快照对象身份复用的前提是该快照在搜索期间不被修改。

相对顺序与路径复制不依赖固定行动数；PP 区间方法可推广到其他有限资源，但必须重新建立其读写合同。当前 PP 身份检查覆盖队伍位置与槽位，而完整单打／双打的自动行动空间仍未实现；现有特殊机制与双打测试是局部语义证据。
