# 求解器原理与代码导航

## 项目方向与优化原则

长期目标是泛用的 Pokémon 对战求解器，不限于 1v1 残局，逐步扩展到完整单打的开局，乃至双打。1v1 是当前优化与验证阶段，不是求解器最终的能力边界。

当前工作是持续改善 1v1 求解的正确性、搜索效率和资源开销，让积累的算法与实现能够支撑更大的对战空间。达到某个 fixture 的时间目标是阶段性证据，不等于已经具备完整单打或双打能力。

- 优先选择基于状态、行动、概率和价值界的通用优化，例如等价转移合并、缓存、证书剪枝和搜索调度，而不是为特定局面定制答案。
- 评估优化时说明其适用条件：是否依赖双方各一只 active、固定行动数或有限 PP；这些条件在换人、队伍对战和双打中是否仍成立。尚未验证的可推广性明确标为未验证。
- 允许有收益且可证明正确的受限优化，但应由实际状态或规则条件决定是否启用，条件不满足时保留正确路径。将局部假设限制在适用范围内，避免成为整个求解器的前提。
- 为未来准备意味着积累可复用的求解能力和清晰的适用边界，不意味着现在提前搭建尚无实际需求的完整单打、双打框架。当前仍以真实 1v1 局面的正确性与实测性能验收。

## 当前求解模型

使用 `@pkmn/sim@0.10.11` 作为战斗规则引擎，并在每个回合求解零和矩阵博弈：

\[
Q_s(a,b)=\sum_{s'}P(s'\mid s,a,b)V(s'),\qquad V(s)=\operatorname{val}(Q_s).
\]

## 随机分支

求解器不会枚举 PRNG 种子。对每个行动组合，它会：

1. 用 `battle.toJSON()` 保存当前状态；
2. 用 `Battle.fromJSON()` 从同一状态重放；
3. 拦截本回合实际发生的 `random(n)` / `randomChance(p, q)`；
4. 当前随机分支就地继续，其它分支排队重放；在已审计的模拟器方法中合并等价随机结果，省略无回调的空事件排序；
5. 未结束的分支按相同后继状态合并并递归求值；终局按胜／负／平效用合并概率，直接计入期望收益。

子状态在必胜行或纯鞍点证书成立时停止展开，其余状态补齐矩阵求解。
根节点仍返回完整收益矩阵和双方策略。随机树与状态空间仍可能随局面复杂度迅速增长。

## 当前边界

这是小状态空间的残局 Demo，提供精确和有界搜索，不是完整生产求解器：

- 支持测试局面会触发的有限离散随机调用；无参数的连续 `random()` 暂不支持；
- 当前自动行动生成只处理双方各一只 active 的招式选择，尚未实现完整换人、6 选 3、双打行动空间；显式双打和换人命令的测试验证的是转移层；
- 假设残局由 PP 保证有限；若存在真正可再生的循环，需要改为随机博弈不动点求解；
- 矩阵求解使用双精度浮点数及收益证书校验，不是有理数符号求解；
- 状态序列化和随机等价优化依赖固定的模拟器实现。升级依赖需重新审计；不匹配的原生方法会保留原模拟路径。

已采用方法的原理、例子与适用边界见[优化技术](optimization-techniques/README.md)，历次实验见[优化记录](optimization-records/README.md)；测量方式见[benchmark 指南](benchmarking.md)。
